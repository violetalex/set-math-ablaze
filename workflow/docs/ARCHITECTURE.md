# 架构

## 一句话

**确定性的部分写成有测试的代码，需要判断的部分交给 agent，两者用文件系统交接。**

## 为什么这样切

这个工作流来自两个真实的数学项目（一个 30 页的条件 Liouville 定理，一个 16 页的
轴对称 NS 分析）。在那两个项目里，出问题的从来不是"算错了"，而是三类：

1. **确定性错误**：脚本静默丢东西（pandoc 吃掉公式编号）、检查脚本误报（把注释里的
   `sorry` 当成真的）、台账与源码对不上。这类错误**可以写成代码**，也应该写成代码。
2. **判断性错误**：证明循环、量词顺序、把条件定理当无条件定理写。这类错误代码查不出来，
   只能靠**独立视角**——另一个 agent、另一个 lens、另一个没参与形式化的人。
3. **纪律性错误**：忘了跑检查、忘了把撤回的命题从摘要里删掉、把 `OPEN` 说成"基本完成"。
   这类错误靠**门禁**和**唯一真相文件**来防。

所以分层是：

```
agent（判断）  ──写文件──▶  docs/*.md + Lean 源码  ──读文件──▶  mathlean check（确定性）
    ▲                                                              │
    └──────────────────── 门禁失败则回炉 ◀───────────────────────────┘
```

agent 之间不直接传状态，只通过文件交接。这样每一步的产物都是可审查、可 diff、可重放的字面量。

## 模块

| 文件 | 职责 | 关键不变量 |
|---|---|---|
| `config.py` | 读 `mathlean.ini` | 配置坏了要给出可执行的提示，不能静默用默认值 |
| `lean_scan.py` | 注释剥离、sorry 扫描、声明抽取 | **行号必须与源文件一致**（保留换行） |
| `audit.py` | 跑 `lake env lean Audit.lean`，解析公理 | 不依赖 `lake build` 的警告文本 |
| `ledger.py` | 台账解析与一致性 | 一条台账行 = 一个可追溯的断言 |
| `checks.py` | 六道门 | 门禁本身出错也要变成一条失败，而不是崩溃 |
| `scaffold.py` | 建工程、vendoring | 生成物必须能独立运行 |
| `doctor.py` | 环境体检 | 每个失败都要给「怎么修」 |
| `selfcheck.py` | 门禁自检 | 每个门都要有一个"故意弄坏"的场景证明它会响 |

## 三个刻意的设计选择

### 1. 注释感知的扫描，而不是正则

第一版用 `re.search(r"\b(sorry|admit)\b", body)`，结果文档里一句
「不允许 `sorry` / `admit`」就让整个门禁红了。

真实的 Lean 有可嵌套的块注释 `/- /- -/ -/`、行注释 `--`、以及含 `--` 的字符串。
扫描器必须按字符走，并且**保留换行**——否则报错的行号会漂移，人就不信它了。

### 2. 台账是 markdown 表格，不是 JSON

因为写台账的人和读台账的人都是人，而且它要进论文附录。
机器可读性通过严格的行格式换取：六列、状态枚举、必填备注词（「假设」「反例」）。

也正因为是给人看的，解析器必须宽容：忽略代码块里的示例、容忍转义的 `|`、
跳过占位行 `| _ | OPEN | ... |`。

### 3. 公理白名单在配置里，不在代码里

不同的数学分支需要的公理不一样（`Classical.choice` 在构造性项目里就不可接受）。
默认值取 Lean 社区最宽松的常用集合，项目可以收紧：

```ini
[axioms]
allowed = propext, Quot.sound
```

自定义公理必须登记并写明论文中对应物——因为"我们引入了一个公理"和"我们证明了"
是两件完全不同的事。

## 扩展点

- **加一道门**：在 `checks.py` 写一个 `check_xxx(cfg) -> Result`，在 `run()` 里加一行，
  在 `selfcheck.py` 加一个"弄坏它"的场景。
- **换学科**：`ledger.py` 的状态机是数学专用的；工程类项目可以换一套状态枚举。
- **换验证器**：`audit.py` 只有 `run()` 和 `parse_axioms()` 两个接口，换成 Coq/Isabelle
  只需重写这两个函数。

## 不做什么

- 不做 Lean 语法分析（`lake build` 才是判定器）。
- 不自动改证明（那是 agent 的活，改了要留痕）。
- 不把 agent 的输出当事实（`workflow.js` 里每个写文件的 agent 都要回报写了什么，
  最后由保真审计和 `check` 交叉验证）。
